## Описание рисков

### Архитектурные риски

**A1 — Потеря данных при CDC-миграции**
Debezium CDC читает transaction log SQL Server. Риск: пропуск событий при сбое коннектора, несогласованность между DWH и Kafka в период dual-write, потеря данных при ротации лога до его чтения.

**A2 — Несовместимость схем событий**
При обновлении продюсера (например, добавлении обязательного поля) старые консьюмеры могут упасть. Риск возрастает по мере роста числа доменных продюсеров.

**A3 — Деградация при dual-write**
В этапах 1–2 данные пишутся одновременно в DWH (через ESB) и Kafka. Двойная нагрузка на SQL Server 2008, не рассчитанный на такую схему.

**A4 — Утечка медицинских данных**
Медкарты, снимки и истории болезни хранятся изолированно в AI/ML домене. Ошибка в ACL Kafka или row policy ClickHouse может предоставить доступ через Self-Service Portal.

**A5 — Vendor lock-in**
Использование managed-сервисов Yandex Cloud (Managed Kafka, ClickHouse, YOS) создаёт зависимость. При изменении ценовой политики или уходе с рынка — сложная и дорогая миграция.

### Организационные риски

**O1 — Нехватка data engineering экспертизы**
Data Mesh требует, чтобы каждый домен самостоятельно поддерживал data products (Bronze/Silver/Gold). Большинство доменных команд не имеют опыта работы с dbt, ClickHouse и DataHub.

**O2 — Сопротивление смене UI**
Врачи и операторы, работавшие с PowerBuilder годами, могут негативно воспринять переход на веб-интерфейс, замедляя внедрение.

**O3 — Отсутствие domain ownership**
Без чёткого назначения Data Product Owner'ов команды будут перекладывать ответственность за качество данных на центральную платформенную команду, воспроизводя монолитную модель.

**O4 — Замедление time-to-market**
Параллельная поддержка DWH + новой платформы требует двойных усилий. Разработчики вынуждены поддерживать обе системы, снижая скорость разработки новых функций.

### Технологические риски

**T1 — SQL Server 2008 EOL**
Microsoft прекратил поддержку в 2019. Система подвержена CVE без возможности получения патчей. Хранение финансовых и операционных данных на EOL-системе нарушает требования безопасности.

**T2 — Операционная сложность Kafka**
Apache Kafka требует навыков управления: мониторинг consumer lag, обработка DLQ, ребалансировка партиций, управление retention и схемами. Ошибки ведут к потере данных или задержкам.

**T3 — Регуляторные требования**
152-ФЗ требует локализации персональных данных; 323-ФЗ и нормативы Росздравнадзора регулируют хранение медицинских данных; ЦБ РФ — требования к финансовым данным и их аудиту.

**T4 — Отсутствие state locking в YOS**
Yandex Object Storage не поддерживает DynamoDB-style locking для Terraform state. Без дополнительных мер возможны конкурентные записи в state файл.

**T5 — Рост стоимости инфраструктуры**
По мере роста объёмов данных и числа доменов стоимость Managed Kafka, ClickHouse и DataHub растёт нелинейно. Без FinOps-практик расходы могут превысить бюджет.
