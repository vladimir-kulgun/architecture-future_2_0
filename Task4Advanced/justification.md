# Обоснование событийного подхода — «Будущее 2.0»

## Текущая ситуация: Apache Camel ESB + DWH

### Как работает интеграция сегодня

```
PowerBuilder UI
      │
      ▼
   Clinic DB (SQL Server 2008)
      │
      ▼  JDBC / SQL
  Apache Camel ESB  ─────────────────────────────────→  DWH (SQL Server 2008)
      │                                                       │
      ▼  REST / SOAP                                          ▼
  Fintech Services                                      Power BI
      │
      ▼  proprietary
  AI Services (Python)
```

Все домены **синхронно интегрированы через ESB**: каждое взаимодействие — это вызов, который требует, чтобы получатель был доступен здесь и сейчас. DWH — единственная аналитическая система, куда стекаются данные из всех источников через ETL.

---

## Проблемы текущей архитектуры

### 1. Жёсткая связанность (Tight Coupling)

| Проблема | Проявление |
|----------|-----------|
| ESB знает о всех получателях | Изменение структуры сообщения в одном домене → ручная правка ESB-маршрутов |
| Синхронные вызовы | Если Fintech Services недоступен — Clinic API падает в таймаут |
| "Умная шина" | Бизнес-логика вытекает в ESB-маршруты (Apache Camel трансформации), а не остаётся в доменах |
| Монолитный деплой ESB | Новый маршрут → деплой всего ESB → риск регрессий для существующих маршрутов |

### 2. Аналитическая пропасть (DWH как bottleneck)

| Проблема | Проявление |
|----------|-----------|
| Пакетная загрузка | Данные в DWH обновляются ночью; бизнес видит вчерашние данные |
| Единая точка отказа | DWH недоступен → нет никакой аналитики ни в одном домене |
| SQL Server 2008 EOL | Нет патчей безопасности с 2019 года; нет возможности вертикального масштабирования |
| Нет разделения по доменам | Все данные в одной схеме; команды зависят друг от друга при изменении схемы |

### 3. Масштабируемость

- ESB — вертикальный сервис; горизонтальное масштабирование сложно
- DWH на SQL Server 2008 не поддерживает современные паттерны sharding/partitioning
- Добавление нового партнёра (фармацевтика) требует написания нового ESB-маршрута и изменения ETL

---

## Событийная архитектура: как это решается

### Принцип «умная конечная точка — тупая шина»

В событийной архитектуре **шина (Kafka) ничего не знает** о семантике событий. Вся логика — в доменах.

```
Clinic API ──→ clinic.visit.completed ──→ [Kafka Topic]
                                              │
                                    ┌─────────┼─────────┐
                                    ▼         ▼         ▼
                               AI Services  Fintech  Data Platform
                               (подписан)  (подписан) (Bronze)
```

Если завтра появится новый подписчик (например, Pharma Service, которому нужно знать о завершённых визитах) — **Clinic API не меняется**. Новый сервис просто подписывается на топик.

## Сравнение: ESB / DWH vs Event-Driven

| Критерий | Apache Camel ESB + DWH | Event-Driven (Kafka + ClickHouse) |
|----------|------------------------|-----------------------------------|
| **Связанность** | Высокая: ESB знает всех получателей | Низкая: продюсер не знает о консьюмерах |
| **Доступность** | Синхронные вызовы: отказ получателя → отказ отправителя | Асинхронно: Kafka буферизует; консьюмер догонит |
| **Добавление нового домена** | Написать новый ESB-маршрут + ETL + деплой ESB | Новый домен подписывается на топики; продюсеры не меняются |
| **Скорость данных в аналитике** | Пакет (ночной ETL); данные с задержкой 1–24ч | Near real-time (Flink); данные в Gold через минуты |
| **Масштабирование нагрузки** | Вертикально (ESB / DWH) | Горизонтально: Kafka partitions + ClickHouse shards |
| **Изоляция доменов** | Все данные в одном DWH; схемы переплетены | Отдельные data products per domain; Gold ClickHouse per domain |
| **Audit / Compliance** | Отдельный ETL для аудита | Audit Log Topic встроен: все события immutable, retention 5 лет |
| **Эволюция схем** | Ручная координация между командами | Schema Registry (BACKWARD_TRANSITIVE): breaking change блокируется в CI |
| **Отказоустойчивость** | SPOF: ESB или DWH упал → всё стоит | Kafka RF=3: broker failure прозрачен; данные не теряются |
| **Новые бизнес-партнёры** | Написать коннектор в ESB, согласовать схему вручную | Kafka Producer API + Schema Registry: подключение за дни |
| **Медицинские данные** | Все данные в одном DWH — сложно изолировать | ACL на топики `med.*` + отдельный AI/ML домен — изоляция на уровне инфраструктуры |

## Конкретные преимущества для «Будущее 2.0»

### 1. Гибкость: новые домены без изменений существующих

**Сценарий:** Подключить Pharma Partner как нового поставщика данных.

- **ESB:** написать новый Apache Camel маршрут, договориться о формате, задеплоить ESB (риск регрессий)
- **Kafka:** Pharma Partner получает Kafka credentials + схему в Schema Registry, публикует в `pharma.drug.*`. Существующие домены не меняются. **Время внедрения: дни vs недели.**

### 2. Масштабируемость: горизонтальное по данным и потребителям

**Сценарий:** Нагрузка на аналитику выросла в 10 раз (открыто 50 новых клиник).

- **DWH:** вертикальное масштабирование SQL Server 2008 — ограничено железом; дорого
- **Kafka + ClickHouse:** добавить партиции в топики; добавить шарды в ClickHouse; добавить реплики Flink-джобов. Линейное масштабирование.

### 3. Скорость реакции: near-real-time вместо пакетного ETL

**Сценарий:** Клиническая операция — врач завершил приём, AI должен запустить анализ немедленно.

- **ESB/DWH:** AI видит данные только после ночного ETL. Анализ — на следующий день.
- **Kafka:** `VisitCompleted` → AI Services получает событие в течение секунд → диагностика запускается немедленно. **Ускорение: часы → секунды.**

### 4. Операционная устойчивость через Decoupling

**Сценарий:** Fintech Services недоступен на 2 часа (плановое обновление).

- **ESB:** Clinic API получает таймаут при попытке синхронного вызова. Операционный процесс в клинике прерывается.
- **Kafka:** Clinic API публикует `VisitCompleted` в Kafka и возвращает ответ пользователю. Fintech Services при восстановлении читает накопленные события и обрабатывает их. **Клиника работает без перебоев.**

### 5. Compliance через встроенный аудит

**Сценарий:** Проверка ЦБ РФ: предоставить лог всех финансовых операций за 3 года.

- **DWH:** специальный аудит-ETL, сложная выгрузка, риск пропусков при сбоях ETL
- **Kafka Audit Log Topic:** все события `fintech.*` записываются immutable с retention 5 лет. Выгрузка — один Kafka Consumer. **Полная traceability без дополнительной разработки.**

### 6. Изоляция медицинских данных как архитектурный принцип

С ESB/DWH изоляция медицинских данных — это соглашение и дисциплина. Данные физически в одной БД.

С Kafka: медицинские данные физически **не могут покинуть** AI/ML домен — Kafka ACL блокирует чтение `med.*` топиков для всех, кроме AI Services. Это не соглашение — это инфраструктурный запрет.

## Риски перехода и их митигация

| Риск | Митигация |
|------|----------|
| Сложность операционного управления Kafka | Managed Kafka (Yandex Cloud) снимает ops-нагрузку; runbook для DLQ |
| Eventual consistency: консьюмер видит данные с задержкой | Проектировать UI под eventual consistency; использовать CQRS-паттерн |
| At-least-once delivery: дубликаты событий | Идемпотентные консьюмеры через `event_id`; `client_request_id` в транзакциях |
| Schema evolution: ломающие изменения | Schema Registry с BACKWARD_TRANSITIVE + CI-проверка |
| Потеря данных при миграции с ESB | Dual-write период + reconciliation job (сравнение счётчиков DWH vs Kafka) |

## Вывод

Переход от **Apache Camel ESB + DWH** к **событийной платформе на Kafka** — это не технологическая замена ради замены. Это архитектурное решение, которое:

1. **Снимает жёсткую связанность** между доменами, позволяя каждому развиваться независимо
2. **Ускоряет time-to-market** для новых партнёров и бизнес-направлений — без изменений существующих доменов
3. **Даёт near-real-time аналитику** вместо ночного ETL — критично для AI-диагностики и финансового мониторинга
4. **Встраивает compliance** (audit log, immutability, retention) как инфраструктурный примитив, а не отдельный процесс
5. **Обеспечивает горизонтальное масштабирование** в соответствии с ростом компании (новые клиники, новые партнёры)
6. **Изолирует медицинские данные** на уровне инфраструктуры, а не только на уровне договорённостей

Для компании «Будущее 2.0», которая одновременно растёт в медицине, банкинге и AI, **событийная архитектура — это фундамент**, на котором новые бизнес-домены могут появляться без блокировки существующих, а данные становятся продуктом, а не побочным эффектом работы систем.
