# Декомпозиция логики ESB (Apache Camel) → целевая архитектура

## Проблема прямой замены

Apache Camel ESB — это **интеграционный движок**, который одновременно выполняет несколько функций: транспорт, валидация, трансформация, маршрутизация, оркестрация бизнес-процессов и интеграция с внешними системами. Apache Kafka — только **транспорт**: надёжная, масштабируемая доставка событий.

Переход «ESB → Kafka» не является заменой 1:1. Каждая функция ESB должна найти нового владельца в целевой архитектуре, исходя из принципа **«правильная логика — в правильном месте»**.

---

## Инвентаризация функций текущего ESB

```
Apache Camel ESB (текущее состояние)
├── ФЛК — форматно-логический контроль (валидация входящих данных)
├── Трансформации (маппинг полей, конвертация форматов: XML↔JSON, SOAP↔REST)
├── Маршрутизация (content-based routing, условный роутинг)
├── Интеграция с внешними системами (JDBC, SFTP, REST, SOAP, HL7)
├── Бизнес-логика (обогащение данных, правила расчёта, агрегация)
└── Оркестрация процессов (многошаговые сценарии, компенсации)
```

---

## Куда расходится каждая функция

### 1. ФЛК — форматно-логический контроль

В ESB: валидация структуры и содержания входящих сообщений до их маршрутизации.

**Целевая архитектура — три уровня защиты:**

```
Продюсер (Domain Service)
  │  Уровень 1: Business validation (до публикации)
  │  • Доменный сервис проверяет бизнес-инварианты агрегата
  │  • Пример: balance ≥ 0 перед TransactionCompleted
  │  • Невалидное событие НЕ публикуется
  ▼
Schema Registry (Apicurio)
  │  Уровень 2: Structural validation (при публикации)
  │  • Avro-схема: обязательные поля, типы, enum-значения
  │  • BACKWARD_TRANSITIVE: новая схема совместима со всеми версиями
  │  • Kafka Producer отклоняет сообщение, не соответствующее схеме
  ▼
Apache Flink (Bronze → Silver)
     Уровень 3: Stream validation (при обработке)
     • Проверка бизнес-правил на потоке (cross-field checks)
     • Пример: visited_at ≤ now(), doctor_id существует в справочнике
     • Невалидные записи → DLQ (dlq.clinic.visit.*) для ручного разбора
```

**Владельцы:** Domain Service (Уровень 1) + Platform (Уровень 2) + Flink Job (Уровень 3).

### 2. Трансформации

В ESB: Apache Camel EIP-трансформации — маппинг полей (BeanTransformer, XSLT), конвертация форматов (XML→JSON, SOAP→REST), нормализация.

**Целевая архитектура — по сложности трансформации:**

| Тип трансформации | Инструмент | Место |
|-------------------|-----------|-------|
| **Простой маппинг полей** (переименование, приведение типов) | Kafka Connect SMT (Single Message Transforms) | В Kafka Connect pipeline |
| **Конвертация форматов** (XML→Avro, SOAP→Event) | Adapter Service (Go/Java микросервис) | ACL-сервис перед публикацией в Kafka |
| **Stateless-обогащение** (добавить поле из конфига) | Flink Map operator | Flink job Bronze→Silver |
| **Stateful-обогащение** (lookup из справочника) | Flink AsyncIO + ClickHouse lookup | Flink job Bronze→Silver |
| **Нормализация данных** (дедупликация, null-handling) | Flink + dbt | Flink (Silver), dbt (Gold) |
| **Бизнес-агрегаты** (SUM, COUNT, windows) | dbt (batch) / Flink (stream) | Silver→Gold |

**Ключевой принцип:** Трансформации Bronze→Silver выполняет **Flink** (streaming). Silver→Gold — **dbt** (batch/incremental). Kafka остаётся "тупой шиной" — только транспорт, никакой трансформации внутри топиков.

### 3. Маршрутизация

В ESB: Apache Camel Content-Based Router — условная маршрутизация сообщений на основе заголовков или содержимого.

**Целевая архитектура — маршрутизация через топологию топиков:**

```
ESB (было):                    Целевая архитектура:
─────────────────              ─────────────────────────────────
Входящее сообщение             Продюсер сам знает нужный топик:
    │                          clinic.visit.completed
    ▼                          fintech.payment.processed
CBR: если тип=VISIT → A        
     если тип=PAYMENT → B      Консьюмер выбирает нужные топики:
     если тип=MEDICAL → C      Flink job подписан на clinic.*
                               AI Service подписан на clinic.visit.*
                               Regulatory подписан на fintech.*
```

| Паттерн ESB | Реализация в EDA |
|-------------|-----------------|
| Content-Based Router | Naming convention топиков: `<domain>.<entity>.<event>` — продюсер публикует в правильный топик |
| Dynamic Router | Consumer Group Subscriptions: каждый консьюмер сам выбирает, что обрабатывать |
| Message Filter | Kafka Streams Filter / Flink FilterFunction — фильтрация на стороне консьюмера |
| Recipient List | Broadcast через партиционирование: несколько consumer groups на один топик |
| Splitter | Flink FlatMap — одно событие → несколько дочерних событий |

### 4. Интеграция с внешними системами

В ESB: Apache Camel компоненты — JDBC, SFTP, HTTP, HL7, SOAP, REST, JMS, файловые адаптеры.

**Целевая архитектура — по типу системы:**

```
Внешние системы
      │
      ├── Реляционные БД (SQL Server DWH)
      │     └── Debezium CDC → Kafka Connect → Kafka
      │         (читает transaction log, не нагружает БД)
      │
      ├── IoT / MQTT (медицинские устройства)
      │     └── Kafka Connect MQTT Connector или
      │         MedDevice Adapter Service → Kafka
      │
      ├── REST API (ЕГИСЗ, ЦБ РФ, внешние партнёры)
      │     └── Adapter Service (Go микросервис)
      │         • Вызывает внешний REST/SOAP API
      │         • Транслирует ответ в доменное событие Kafka
      │         • Является Anti-Corruption Layer
      │
      ├── HL7 FHIR (медицинские стандарты, ЕГИСЗ)
      │     └── HL7 Adapter Service
      │         • Парсит HL7-сообщения
      │         • Публикует нормализованные события в med.egisz.* топик
      │
      ├── SFTP / файловые источники (отчёты, выгрузки)
      │     └── Kafka Connect File Pulse Connector или
      │         ETL-джоб (Python) → Object Storage → Flink batch
      │
      └── Kafka-совместимые партнёры (Pharma, MedDevice)
            └── Напрямую в Kafka через Schema Registry
                (без адаптера)
```

**Adapter Service** — новый класс компонентов, которых не было явно в исходной диаграмме. Это лёгкие Go/Java микросервисы, каждый отвечает за интеграцию с одной внешней системой. Они наследуют роль Camel-компонентов, но живут как доменные сервисы, а не в монолитном ESB.

### 5. Бизнес-логика

В ESB: Apache Camel Bean Processor, скрипты Groovy/Java, кастомные компоненты с расчётами, правилами, обогащением.

**Это самая критичная проблема текущего ESB.** Бизнес-логика в интеграционном слое — антипаттерн. При миграции она должна переехать в доменные сервисы.

```
Инвентаризация бизнес-логики ESB:
┌──────────────────────────────────────────────────┐
│ Тип логики                │ Куда переезжает       │
├───────────────────────────┼───────────────────────┤
│ Расчёт кредитного рейтинга│ Fintech Credit BC     │
│ Проверка доступности слота│ Clinic Patient Flow BC│
│ Расчёт стоимости процедуры│ Clinic Clinical Ops BC│
│ Валидация лимита платежа  │ Fintech Banking BC    │
│ Обогащение справочниками  │ Flink lookup join     │
│ Расчёт KPI-метрик         │ dbt (Gold layer)      │
│ Нотификации (SMS, email)  │ Notification Service  │
└───────────────────────────┴───────────────────────┘
```

**Принцип:** Логика принадлежит домену, который понимает её бизнес-смысл. ESB никогда не должен был содержать бизнес-правила — это техдолг, который миграция обязана устранить.

### 6. Оркестрация процессов

В ESB: многошаговые Apache Camel маршруты, Saga-реализации, компенсирующие транзакции.

**Целевая архитектура — два паттерна в зависимости от сложности:**

#### Choreography (для простых цепочек)
Каждый сервис реагирует на событие и публикует следующее. Нет центрального оркестратора.

```
VisitCompleted
    │
    ├──→ Flink Job: ItemConsumed (списание инвентаря)
    ├──→ Fintech BC: выставить счёт → PaymentInitiated
    └──→ AI Service: запустить диагностику → AIStudyCompleted
```

Подходит для: линейных цепочек без длительного ожидания, без сложных условий ветвления.

#### Orchestration via Temporal (для долгосрочных процессов)
Для многошаговых бизнес-процессов с timeout, retry, компенсацией.

```
Temporal Workflow: CreditApplication Process
┌─────────────────────────────────────────────┐
│ 1. ValidateApplication (sync, 30s timeout)  │
│ 2. RunCreditScoring (async, up to 24h)      │
│ 3. if approved: CreateCreditAgreement       │
│             else: NotifyRejection           │
│ 4. SetupRepaymentSchedule                   │
│ 5. Compensation: если шаг 4 упал →          │
│    RollbackCreditAgreement                  │
└─────────────────────────────────────────────┘
```

Temporal хранит состояние процесса, обеспечивает retry и visible history. Подходит для: кредитные заявки, онбординг пациента, регуляторные отчёты с multi-step approval.

**Saga Choreography** (через Kafka) применяется для распределённых транзакций между доменами:

```
PatientRegistered (Clinic)
    │
    └──→ AccountOpened (Fintech BC реагирует)
             │
             └──→ если AccountOpened.failed →
                  Clinic BC получает CompensationRequested →
                  Patient переводится в PendingActivation
```

## Что это означает для миграции

### Этап 1: Инвентаризация логики ESB (до начала кода)

Перед заменой ESB необходимо пройти каждый Apache Camel маршрут и классифицировать логику:

```
Для каждого маршрута:
1. Что это делает? (ФЛК / трансформация / маршрутизация / интеграция / бизнес / процесс)
2. Куда переедет? (Domain Service / Flink / dbt / Adapter / Temporal)
3. Кто владелец? (какой домен несёт ответственность?)
4. Есть ли тесты, которые докажут эквивалентность поведения?
```

### Этап 2: Параллельная работа (Strangler Fig)

```
Период миграции:
ESB маршрут X (работает) ──────────────────────────────→ вывод
         │
         └── новый путь (Domain Service + Kafka + Flink) → Shadow
                                    ↓
              reconciliation: выходы ESB == выходы нового пути?
                                    ↓
                          да → переключить трафик → вывести ESB маршрут
```

### Этап 3: Вывод ESB

ESB выводится только когда:
- Все маршруты декомпозированы и протестированы
- Reconciliation показывает 100% совпадение (счётчики записей, checksum ключевых полей)
- Runbook для каждого Adapter Service и Flink-джоба задокументирован
